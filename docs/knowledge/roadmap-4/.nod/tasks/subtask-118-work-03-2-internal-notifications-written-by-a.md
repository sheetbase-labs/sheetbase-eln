## Work Log
  -  validation_error landed too, with its behaviour verified end-to-end against the development database rather than by a test: drizzle/0389 patches api.flag_dataset_value to emit a dataset change event carrying {action: value-flagged} and adds a trigger branch that notifies the dataset's creator, skipping whoever set the flag. Verified by flagging a real seeded dataset value: the change event carries the action payload, and no notification is written when the flagger is the creator (the self-skip). A test file was written and removed because its fixture could not work as constructed - the dataset it created was invisible to the migrator connection it queried through (api.datasets is RLS-protected, and a migrator-role connection without claims does not see rows the authenticated caller would), and writing the schema fields required the draft-then-publish order because a published version's fields are immutable. The fixture needs to create the dataset through the canonical RPCs with claims, which is the next step for this test. Seven of the eight design event types now derive; only material_expiring remains, which needs a reagent expiry sweep that does not exist.
  -  signature_requested landed too: api.request_signature_witness already emits a review_submission update whose payload carries {action: witness-requested, witnessUserId, requestId, submissionId}, so no new producer was needed - the trigger reads that payload and addresses the witness, skipping the requester. drizzle/0388, verified by tests/db/witness-signature-notification.test.ts (2 cases: the witness is notified, a witness who requested their own signature is not). Six of the eight design event types now derive: review_requested, review_returned_or_signed, comment_or_mention, protocol_new_version, instrument_booking and signature_requested. Remaining: validation_error (the check runner would have to emit) and material_expiring (a reagent expiry sweep, which does not exist - reagent_attention_summary is read-time only).
  -  RESOLVED and landed: the booking notification works. Two things were wrong. First, a generic trigger (trg_change_event_calendar) already emits a booking change event, so no new emitter was needed for the event itself - but it fires when the booking row is inserted, which is BEFORE the RPC writes the participants, so the notification found nobody. api.create_booking therefore emits again after the participants exist, and the notification trigger's instrument_booking branch addresses them. Second, my first attempt's idempotence guard tested for the table name, which the function mentions anyway, so the emit was silently skipped; it now checks for emit_change_event. Verified end-to-end by tests/db/booking-notifications.test.ts: a booking with two participants writes the change event and notifies the other participant, never the booker. Still open for this step: signature_requested, validation_error and material_expiring.
  - 2026-10-10: the booking producer landed, and the notification half hit a wall worth recording. drizzle/0387 patches api.create_booking to emit a calendar_booking change event (verified: the event appears for a created booking) and extends internal.notify_from_change_event with an instrument_booking branch that addresses the booking's participants. The branch runs and raises nothing, but inserts no notification: the SELECT inside it finds no participants, even though api.calendar_booking_participants holds them. The trigger is SECURITY DEFINER and the participants table carries RLS (policies for authenticated and api_client, plus internal.can_access_object), so the visibility of those rows to the trigger's execution context is the thing to establish before this branch can work - the existing branches read api.review_submissions and api.comments, which behave. A test for the notification half was written, failed on exactly that lookup, and was removed rather than left failing; the emitter itself is a genuine improvement and stays. Remaining for this step: signature_requested, validation_error and material_expiring have the same no-producer problem, and this booking notification needs the participant-visibility question answered.
  - 2026-10-10: extended (drizzle/0381; tests/db/notifications.test.ts, 6 cases). Beyond review_requested and review_returned_or_signed, the trigger now derives comment_or_mention (the record's author and every mentioned user) and protocol_new_version (everyone trained on that protocol), honouring api.notification_preferences.in_app, skipping the actor, and warning rather than blocking the observed write if derivation fails. Still open in this step: signature_requested, validation_error, instrument_booking and material_expiring have no producer - nothing emits a change event for a witness request, a check result, a booking or a hold transition - so they land with those flows (CAL, EXP, LAB) rather than being guessed here. Note for future migrations: drizzle/0358 had already extended this same function with the LAB-07 training reminders, and the reminder suite caught the omission when this migration first rebuilt it; the current definition is the merge of both.
