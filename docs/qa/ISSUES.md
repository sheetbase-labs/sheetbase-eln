**Where the risk sits.** The four issues to fix first are the ones where the app tells the user
something untrue or does nothing at all: the Inbox list rendering rows that do not match the active
filter (C5), the import rejection naming a cause that is false for the dataset (C7), the saved-view
“Update” that silently writes nothing (C9), and the model record form whose required category field can
never validate (C6). Then the two that block a user outright — a booking with no cancel path (C8) and
the account control unreachable at 320 px (C13) — then the intermittent create-project dialog (C3,
needs a decision because it is not reproducible on demand).

**How to read the status column**: `confirmed (UI)` was driven in a browser and observed;
`confirmed (HTTP)` was driven through the app's own endpoints when the browser was unusable;
`static` was established by reading the source; `reviewer` means a reviewer reported it with evidence
in their file; `unconfirmed` needs a re-run before it is treated as a defect; `retracted` is recorded
for completeness and is not work.

**Two ids, one defect** (kept separate because they came from independent passes with different
evidence): `QA3-records-1` and `QA3-import-1` both describe the import rejection message that names
a false cause — the first found it through the UI, the second found the mechanism in the source;
`QA3-C3` is the coordinator's re-test of the behaviour the lists reviewer saw work once.
