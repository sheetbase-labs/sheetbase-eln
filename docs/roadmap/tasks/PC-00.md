# PC-00 — Product & Platform Consolidation Audit

**Status:** COMPLETE  
**Implementation:** audit/planning only (no product code)  
**Depends on:** CORE-01–06 and Core Hardening complete  
**Evidence:** [`../audits/PC-00.md`](../audits/PC-00.md)  
**Hand-off:** `docs/roadmap/NEXT.md` uses parallel streams. PC-01 (Medium, Ready) and API-01 (Low, Ready) are the first assigned work.

## Goal

Establish the real post-Core product/platform starting point before committing to implementation epics.

The audit should answer:

> What can a scientist, Steward, administrator and external developer actually do in Sheetbase today, which paths are canonical, what is missing, and what should be built first?

This is broader than a UI audit.

## PC-00.1 — Product surface inventory

Catalogue routes, navigation, entry points and major components.

For each surface classify:

- `CANONICAL PRIMARY`;
- `SUPPORTING`;
- `INTERNAL/ADMIN`;
- `DUPLICATE/OVERLAPPING`;
- `OBSOLETE/DEAD`;
- `MISSING PRODUCT SURFACE FOR EXISTING CORE CAPABILITY`.

Include Sheets, Datasets, Records, Notebooks, Templates, configuration, history/evidence and specialist/paused workspaces.

## PC-00.2 — Sheet workflow audit

Exercise and inspect:

- blank ad-hoc Sheet creation/edit;
- row/column creation;
- paste/edit behaviour;
- calculations;
- ad-hoc → composed transition;
- Dataset/Record binding;
- Record link/create;
- local + governed data together;
- sorting/filtering/presentation;
- provenance;
- write-back;
- promotion;
- Definition extraction/reuse;
- Definition upgrade;
- materialisation;
- Notebook embedding;
- reload/conflict/error behaviour.

Identify backend capabilities with no usable Sheet affordance.

## PC-00.3 — Dataset & Record workflow audit

Assess catalogue/discovery, create/edit, import/paste, query, schema/version visibility, immutable Versions, relationships, bulk operations, lifecycle, dependencies, export and navigation into related work.

## PC-00.4 — Notebook & Template workflow audit

Assess Notebook authoring, blocks, multiple Sheets, references, files, history, submission/frozen rendering, amendments, Template creation/versioning, parameter mapping, instantiation, upgrade and reuse.

## PC-00.5 — Configuration/governance audit

Assess Models, fields, Dataset Schemas, Definitions, Templates, vocabularies, dependency/impact visibility, lifecycle, promotion/evolution, roles/capabilities, invitations and administrative boundaries.

## PC-00.6 — API/developer-platform audit

Map current external API and distinguish deliberate public contracts from internal PostgREST/RPC implementation.

Assess credentials/service identity, API versioning, errors, pagination, bulk operations, idempotency, concurrency, documentation/OpenAPI, SDKs, events/webhooks and browser/API parity.

## PC-00.7 — Data interoperability audit

Assess CSV/XLSX/JSON/clipboard import, mapping/validation, export, files/attachments/object storage, checksums, search and portability.

## PC-00.8 — Collaboration & analysis audit

Assess existing comments, presence, notifications/review, charting, analysis, formula/visualisation remnants and whether old specialist surfaces should be reused, converged or left paused.

## PC-00.9 — Integrations & platform audit

Assess connector/instrument remnants, deployment, migrations, backups/restore, observability, security controls, administration and representative performance evidence.

## PC-00.10 — Golden workflow exercise

Walk at least these workflows end-to-end where current functionality permits:

1. simple assay Notebook;
2. purification experiment with multiple Datasets and Records;
3. paste → resolve/create Records → governed data;
4. ad-hoc exploration → governed/reusable structure;
5. reusable Notebook Template with typed parameters;
6. submit/freeze → mutate live state → historical render.

Record dead ends, duplicate paths, missing actions and confusing state transitions.

## PC-00.11 — Gap and priority model

Classify findings:

- `P0` correctness/security/data-loss blocker;
- `P1` blocks coherent product/platform use;
- `P2` important capability/consolidation gap;
- `P3` cleanup or later enhancement.

Separate architectural defects from missing product surface and from deliberately deferred functionality.

## PC-00.12 — Refine roadmap

Using evidence, refine the first implementation epics across PC/API/DATA/GOV/PLAT.

For each proposed near-term epic provide:

- goal;
- dependencies;
- user/platform outcome;
- production surfaces;
- data/API/security implications;
- focused acceptance criteria;
- principal risks;
- suggested parallelisation.

Do not automatically activate every programme.

## Exit

PC-00 is complete and accepted. Evidence: [`../audits/PC-00.md`](../audits/PC-00.md). `NEXT.md` uses parallel streams: PC-01 (Medium, Ready) and API-01 (Low, Ready).

## Do not

- do not implement fixes during the audit;
- do not start AUTO;
- do not redesign settled Core architecture without concrete defect evidence;
- do not revive old specialist surfaces merely because code exists;
- do not confuse missing UI with missing backend contract;
- do not treat current PostgREST exposure as automatically equivalent to the intended public API.
