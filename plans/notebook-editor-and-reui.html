  1. The benchmark is Notion, and the requirement is that the notebook behaves like one document. Stated plainly by the owner: the editor is janky and blocky, it does not feel like one document, the blocks must stay because they carry the information, and it should feel like Word — put a caret anywhere and type. Notion is the right example, because Notion is a block document whose text reads continuously. That splits Part A cleanly: first make the surface behave continuously (A2), then make prose genuinely one text flow (A3). Both are additive; neither moves canonical state. Prose already is Tiptap, and the slash menu already calls itself Notion-style (slash-command-menu.tsx:10, notebook-document.tsx:754), so this is finishing a surface, not replacing an engine. One boundary is stated rather than implied, because it is a standing product rule: PRODUCT.md:159 rules out “a Notion clone with scientific icons added afterwards”. Adopting Notion’s document mechanics is decided; copying its visual identity — its greys, its rounded hover cards, its generic page tree — is not, and the tokens plus the design-parity gate are what hold that line.
  2. The load-bearing decision is to keep the rows canonical and give one editor a run of them, rather than replacing the rows. Block identity is what comments, signatures, protocol pins, revision diffs, frozen sheet evidence and the submit digest hang off. A single ProseMirror document as source of truth would either move canonical state out of the row model — against the explicit no-shadow-persistence rule — or require a bidirectional projection over it. The measured middle is a run-scoped editor: one Tiptap instance spans each maximal run of consecutive prose blocks, nodes carry their originating row identity, and the editor writes per-row updates. Caret, selection and Cmd+Z then behave as one document within prose, which is exactly the behaviour asked for, at a fraction of the risk. Across a non-prose block (a sheet, a chart, a plate map) traversal stays block-to-block, as it must — no editor can put a caret inside a gel image.
  3. The Tiptap Notion-like template is a reference, not a dependency. Its production use requires a paid Start plan; its collaboration is Tiptap Cloud over Yjs, which contradicts two written decisions here (PostgreSQL is the only authority for scientific state; Liveblocks is the realtime substrate with no canonical content in rooms); its node set (maths, emoji, mentions, images, AI) exceeds the closed rich_text payload contract; and Tiptap’s own docs still recommend React 18 while this repo is on React 19.2. Copy the free MIT pieces that fit; do not import the template.
  4. The genuine extensibility problem is not the editor — it is that one block type is declared in eight places. Adding a type today means touching the BlockType union, KNOWN_BLOCK_TYPES, the chk_blocks_type migration, the validator map, the picker catalogue, two switch statements, defaultPayloadFor, and the editable/wide sets. A single block registry is the change that makes Part A and every future block cheap. Do this first
  5. ReUI was already adopted here once, and then deleted. The registry alias is configured, an ESLint exception is still reserved for it, and src/components/reui/** no longer exists — it was removed alongside the retirement of the legacy-shell routes (38b9e47a-era work; UI_PORT.md:189-191). So Part B is not “should we adopt ReUI”, it is “what is the bar for the second attempt”.
  6. ReUI’s best fit is generic UI, and its worst fit is this repo’s scientific surfaces — so the sweep needs a comparative method, not a preference. The agreed default is: if ReUI has a component for the job, evaluate it. An A/B harness (§4.5) renders ours and theirs on identical data with a fixed behavioural checklist, so “theirs is better” becomes evidence. Two exclusions are already decided: the sheet grid stays @sheetbase-labs/sheetbase-table (ADR-0048), and the figure renderers stay in-house. Data grids and table framing are the first targets, and both need TanStack Table v9 — decided in scope — against the current v8.21.3.

2.4 Three things the audit turned up that matter more than they look

Defect-class finding

Three block types can be inserted but not edited. callout, table and metric are offered by the picker and rendered by the preview, but have no BlockEditor case and fall through to UnsupportedEditor (block-editor.tsx:192-236, :1576-1605). sheet bypasses the switch entirely and is rendered by the document. A Notion-like authoring surface makes this contradiction visible to the user on day one — you can type /table, get a table, and then not be able to put anything in it.

Contract drift

The sheet payload has two contracts. The application validator accepts only { instanceId, presentation? } (src/lib/blocks/index.ts:271-310), while the database trigger additionally permits tableId and templatePlacementId (drizzle/0120:120-131). Two writers with two answers is exactly the kind of divergence a registry removes.

Evolution gap

payload_schema_version exists but cannot advance. The column is real and the validator reads it, but every type accepts version 1 and only 1 (src/lib/blocks/index.ts:137, :944-981). There is no version-keyed reader and no upcaster, so any payload change is a flag day rather than a migration. If the plan is to be “future-proof”, this is the mechanism that has to exist first.

2.5 A second sheet path still exists

The notebook’s sheet block embeds a canonical Sheet Instance and renders CanonicalSheetWorkspace over @sheetbase-labs/sheetbase-table (ADR-0048). Separately, the older ScientificSheetBlock and ScientificWorkbookProvider against scientific_tables are still present in src/components/sheet/. The product rules say one canonical path per concept and no shadow persistence (system-overview.md:114-117, non-goals.md). This is not Part A’s job, but Part A’s shell must not deepen it, and the plan should name it as pre-existing debt.

3.3 Three architecture options

Option A1 — Shell plus run-scoped editor, rows kept canonical Chosen

Keep api.blocks canonical and per-block optimistic versions exactly as they are. Build the missing document behaviour on top in two steps: (1) a shell that makes the surface continuous — unified gutter rail, one reorder mechanism (dnd-kit), placeholders, block-to-block traversal that reads as one page; then (2) a run-scoped editor, where one Tiptap instance covers a maximal run of consecutive prose blocks, so caret, selection and undo span the run as one text flow while the rows underneath stay individually versioned and individually addressable.

Cost: moderate for step 1, moderate-to-large for step 2. Buys: the felt difference between “a form with blocks” and “a document”, without a model change. Step 1 is a strict prerequisite of step 2, so nothing is discarded.

Option A2 — One root ProseMirror document as the source of truth

Every block becomes a node in a single Tiptap document, and the ordered list is derived from the document rather than the reverse. This is what Notion actually is, and what the Tiptap template assumes.

What it breaks unless re-architected: canonical row identity for comments and signatures; per-block optimistic concurrency; per-block revision diff; frozen sheet-evidence pinning; digest canonicalisation of payload.frozen.revisionId; unknown-type preservation as readable placeholders; per-block offline drafts. Persisting root PM JSON as canonical would also violate the explicit “no second model / no shadow persistence” rules. The alternative — a bidirectional projection with per-block reconciliation — is correct but is a rewrite of the save path, the diff engine and the anchor model.

Verdict: Reject — A1 step 2 delivers the same user-visible result for prose, which is where the requirement actually lives.

Option A3 — Adopt Tiptap’s Notion-like template

A prebuilt block editor with slash commands, drag-and-drop, floating toolbar, emoji, mentions, maths, image upload and AI.

  • Licence: production use requires at least Tiptap’s Start plan; it is not an open-source drop-in.
  • Collaboration: Tiptap Cloud over Yjs, requiring TIPTAP_COLLAB_* JWTs. That contradicts ADR-level decisions here: PostgreSQL is the only authority for scientific state, and Liveblocks already holds presence and comments with no canonical content.
  • Runtime risk: Tiptap’s own docs say the UI components “work best with React 18” and React 19 support is in progress; this repo is React 19.2.
  • Fit: its node set exceeds the closed rich_text contract and its visual language would have to be rebuilt against this repo’s tokens and design-parity gate anyway.

Verdict: use as a feature reference and copy specific MIT-licensed extensions and UI components; do not import the template.

A2 — Making the surface continuous

The visible gap is that consecutive prose blocks read as separate cards. Treat a maximal run of consecutive rich_text blocks as one prose run: one continuous column, no per-block chrome for interior members, no gap between paragraphs, insertion and traversal that behave as though the rows were not there. This is rendering and keyboard-model work with no payload, migration or evidence consequence, and it is the highest-yield item in Part A. It satisfies D6–D7 and most of the perceived jank on its own.

A3 — The run-scoped editor, and why it is the part that actually feels like Word

Continuity of appearance does not give continuity of text. As long as each row is its own Tiptap instance, the caret cannot cross a boundary, selection cannot span rows, and undo resets between them — which is precisely the jank being reported. The fix is to give one Tiptap instance a whole run, while the rows remain the storage:

The run-scoped editor contract
ConcernContract
Editor scopeOne Tiptap instance per maximal run of consecutive rich_text rows. A non-prose block, a heading of another block type, or any structural break ends the run.
Row identity inside the documentEach node carries the id of the row it came from (a node attribute, set by a plugin on load and on edit — the same technique already used here to project outline anchors). Identity lives in the editor, never in the payload, exactly as ADR-0025 requires.
LoadingConcatenate the runs’ payload docs in order, stamping each node with its source row id.
WritingOn change, group nodes by their row id and write only the rows whose content changed, each with its own p_expected_version. Rows are still updated through update_block_payload; no new write path, no bulk endpoint.
New nodesText typed at the end of a row joins that row. A new node created by Enter attaches to the current row unless the writer decides the row is over its size guidance, in which case it becomes a new row after it (a structural insert, as today).
Boundary removalBackspace-join may remove a row boundary. The row is deleted through delete_block only when it carries no anchors that would be orphaned — no comment thread, no signature-relevant reference. Otherwise the row is kept and reduced to an empty paragraph. This is the rule that keeps D3 from silently destroying evidence.
ConflictsUnchanged in principle, finer in practice: a stale row inside a run fails its own version check and surfaces the existing conflict banner for that row, rather than the whole run failing.
OfflineDrafts remain per row in the device store; the run is assembled from drafts plus server state on load.
Frozen revisionsUntouched. The frozen path reads row snapshots and never mounts an editor.
The one genuinely hard part

Split boundaries must be stable enough that a run can be re-split into the same rows it came from. The design above makes identity explicit (node attributes) rather than positional, which is what makes D3, D4 and D7 tractable — but it is the part of this plan most likely to hide surprises, and it deserves its own spike before A3 is estimated with confidence. If the spike fails, A2 still ships the appearance and the plan stops there without waste.

4.2 What ReUI is, and how it installs here

  • Not an npm package. Items are installed with the shadcn CLI from a registry namespace: npx shadcn@latest add @reui/<name>. You own the source afterwards.
  • Two primitive builds. Every item ships as Base UI and as Radix UI; the style token is {base}-{variant}, so radix-nova (current pin) and base-nova are both valid.
  • Scale. 27 custom primitives and 1,264 free examples across 87 categories; 648 Pro blocks requiring a licence key; 667 icons in 4 styles under an Ultimate licence.
  • Class merging. Newer items import cn from the cn package rather than the repo’s local #/lib/utils helper, so an adoption introduces that dependency.
  • Relevant to the notebook: the free Sortable primitive is dnd-kit based, which is exactly the replacement for the hand-rolled HTML5 drag in notebook-document.tsx.

4.3 The variant decision this repo has to make

There are two UI generations in the tree, with a test enforcing the direction of travel:

Recommendation: base-nova (or base-mira for compact density), plus the amendment. See decision 1.

4.4 The bar for adopting a ReUI component

Agreed policy (owner, 2026-10-15): where ReUI has a component for a job we hand-rolled, we evaluate it. The catalogue is the starting list, not a shortlist; tables and data grids are called out as the first targets, and anything scientific is excluded up front. What follows is how “evaluate” stays honest rather than becoming a preference.

Two repo rules make this more than a taste question: new screens must compose existing components before introducing new primitives, and the design-parity gate accepts a screen only when it matches its design render. So an adoption is an exception, and each one must carry a reason. Proposed bar — all five must hold:

  1. The component serves a generic UI job (grid, sort, upload, steps, dates, empty, tree), never a scientific or domain surface.
  2. The hand-rolled version it replaces is materially worse, not merely different: a named behaviour is missing, or the maintenance burden is demonstrably ours.
  3. It is restyled to Sheetbase tokens — no palette classes, no hex, no second design language — and passes the colour check, axe and the adoption guard.
  4. It replaces the old component in the same change. No parallel implementations.
  5. Where the screen is in the design set, its parity row is updated; where it is not, a story plus a browser test stands in.

11.3 Four findings that change the shape of Part B

11.3.1 A plain install would re-introduce the deprecated kit

@reui/data-grid declares bare registry dependencies — button, checkbox, input, popover, select, separator, skeleton, spinner, dropdown-menu — and the shadcn CLI resolves a bare name into aliases.ui, which here is #/components/ui: the legacy Radix kit that ADR-0055 decision 1 says is not extended. Nine of those files already exist in that directory, and select, separator and spinner have no v3 twin at all, so an install would write fresh Radix primitives into the kit the app migrated away from. The adoption guard would not object: it is import-graph only.

Method: install into a scratch directory, read the item there, and place the files by hand under src/components/reui/**, wiring the v3 twins that already exist. This is a step in every adoption below, not a one-off for the grid.

11.3.2 Every copied item's class merge must be re-pointed to ours

ReUI items import cn from the cn package. This repository's helper is src/lib/utils.ts:15 — a cn that teaches tailwind-merge the Sheetbase type scale precisely so text-body and text-fg are not treated as one utility group, and all 27 v3 primitives import it. Left alone, a copied item silently loses that and the class-merge bug returns. Re-pointing the import is exactly the “import-path fix” ADR-0055 decision 2 permits, and it means cn is never added as a dependency.

Two facts verified from the registry itself, which go with it: items carry files[].target — sortable lands at components/reui/sortable.tsx — so the destination needs no CLI flag; and the free items are MIT and key-free, so decision 3 is undisturbed.

11.3.3 TanStack Table v9 is real, and it is one file

The grid is written against v9 exactly, and the v8 declare module augmentation is ignored by any table built with dataGridFeatures. That is the prerequisite this plan named — but the repository has one v8 table, not many, so the migration stops being Part B's largest risk. It still comes first, because no grid can be evaluated before it.

11.3.4 Install names are not page slugs

File upload's registry item is @reui/use-file-upload while its page is /components/file-upload. empty, combobox, kbd, marker, trace, chart, table and pagination are stock shadcn items on the same index and install by bare name. Every adoption therefore starts by reading the install command from the item's own page — https://reui.io/docs/components/base/<name>.md — or by asking the ReUI MCP server for the component, rather than guessing a name from a slug.

11.5 What an adoption must clear

In order, with the command. The proof is the run, not the workflow file: Roadmap 5's own notes record that hosted CI has never executed on this repository (PLAT-03), so CI is the gate as written rather than as observed.

  1. pnpm check — prettier, plus scripts/check-colours.mts: no palette class, no hex and no rgb() in src/**/*.{ts,tsx} outside a three-file allowlist. This is the colour check ADR-0055 means; the design submodule's check-design.py is not one.
  2. pnpm lint — src/components/reui/** is the only relaxed path.
  3. pnpm typecheck.
  4. pnpm test — includes the adoption guard (src/components/v3/ui/component-adoption.test.ts), the component axe gate, the contrast pairs and the token-mapping pin.
  5. pnpm build; and pnpm generate-routes when a route is added.
  6. The Playwright browser suite — where the stand-in for a screen with no design row lives.

Two caveats make that last step load-bearing rather than mop-up. The parity suite compares 45 screens across two themes, but parity.spec.ts:126-131 fails while DESIGN_PENDING is non-empty and 81 of 126 boards are still pending, so pnpm test:parity is red today by construction and cannot be the evidence that an adoption is clean. And Storybook is checked nowhere — 77 stories, absent from pnpm validate and from CI, with the adoption guard skipping them — so “a story stands in” is documentation, not verification. Only four of the seven Tier-1 targets touch a screen in the parity set; for the rest, the browser test is the whole proof.

Two further traps: src/styles.css carries two token vocabularies — the ELN semantic set at :336 and the app-3 bridge at :683-707 that the v3 kit actually writes — so a copied component using bg-card will render, look wrong beside every neighbour, and pass the colour check; and the guard's replacement rule is keyed on a basename collision with a v3 twin, so an adopted component that keeps a ReUI-internal name is invisible to it.
